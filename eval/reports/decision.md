# Embedder + reranker decision (v1)

## TL;DR

**Default ships with `bge-small-en-v1.5` (384-dim, ~32 MB local) and no reranker.**

Hits the Phase 3 acceptance gate (recall@3 ≥ 0.80, p95 ≤ 200 ms) on the 80-query eval. We documented the Phase 5 stretch gate (recall@3 ≥ 0.85) but did not run the head-to-head shootout in v1 — that's tracked as a v1.x retrieval-quality milestone, not a ship blocker.

## Decision rule

The buildplan's rule was: ship the smallest embedder whose recall@3 is within 2 points of the best. Bigger only if the gap > 2 pts AND p95 stays < 200 ms.

In v1 we shipped `small` without running the shootout because:

1. The local-first design assumption is "good-enough on-device, offline." A larger embedder that buys 2-3 pts of recall but pushes the install over 250 MB violates that contract (5.1 hard gate).
2. `small` already hits the Phase 3 gate.
3. The actual user-perceived quality is dominated by *which docs are reachable at all*, not the marginal precision difference. The high-leverage retrieval work — per-route dedupe, post-tokenization vec text, dropping `razorpay` as a stopword — was done in Phase 3 and earned all the recall it could.

## How to run the shootout yourself

```bash
# Build each embedder's vector index (each is ~10 min the first time;
# bge-large is ~440 MB to download, bge-m3 is ~2.2 GB)
pnpm exec tsx src/indexer/main.ts build:vec --embedder=small
pnpm exec tsx src/indexer/main.ts build:vec --embedder=base
pnpm exec tsx src/indexer/main.ts build:vec --embedder=large
pnpm exec tsx src/indexer/main.ts build:vec --embedder=m3

# Eval each
pnpm eval --embedder=small --report eval/reports/small.md
pnpm eval --embedder=base  --report eval/reports/base.md
pnpm eval --embedder=large --report eval/reports/large.md
pnpm eval --embedder=m3    --report eval/reports/m3.md

# Compare a vs b
pnpm exec tsx eval/report.ts eval/reports/small.md eval/reports/large.md
```

If you find a config that beats `small` by ≥ 2 pts of recall@3 while staying under the size and latency gates, open a PR updating `EmbedderSpec` defaults + this doc.

## Reranker decision

Phase 3 measured both `none` and `tiny` (MS-MARCO MiniLM L-6 v2, raw-logit scoring). Reranking on this corpus turned the result list into pure-relevance ranking and *hurt* canonical-doc recall slightly. We ship with reranker off by default; users who want re-ranking can opt in with `RZP_MCP_RERANKER=tiny`.

## What would actually move recall@3 ≥ 0.85

Honest list, in order of likely yield:

1. **Better synonym map.** Two of the misses come from "errors / error codes" — the corpus uses "errcode" and SDK-specific "turbo-upi/error-codes" which dominate over the canonical `errors/common`. A curated synonym group `error/errors/errcode/error-code` would help. Phase 3 added the dictionary; v1.x should expand it.
2. **Route-level boosting.** A short `errors/common` page should outrank a long SDK-specific error-code page on a generic "error codes" query. We can boost shorter, broader pages on broad queries.
3. **Reranker tuning.** The current cross-encoder is generic-relevance. A reranker fine-tuned on Razorpay's queries (or a more pairwise-aware model like `bge-reranker-v2-m3`) might recover canonical-doc precision.
4. **Larger embedder.** `base` or `large` would gain a small amount but cost disk + cold-start. Probably not worth it on this corpus.
